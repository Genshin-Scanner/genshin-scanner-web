# Архитектура v1 браузерного видеосканера Genshin Impact

## Цель первой версии

Игрок выбирает локальную запись, просматривает извлечённые карточки, исправляет спорные поля и скачивает GOOD v3. Первый поддерживаемый сценарий — инвентарь артефактов 4★ и 5★, английский интерфейс игры на ПК, MP4/H.264. Приёмочные записи имеют форматы 16:9 и 16:10. Сайт собирается Vite для GitHub Pages. Обработка происходит на устройстве в настольных Chrome, Edge, Firefox и Safari.

## Монорепозиторий

Bun управляет workspace-пакетами, зависимостями, lock-файлом и командами проверки. Vite собирает сайт и самостоятельные ESM-библиотеки, TypeScript выпускает декларации для потребителей. Пакеты импортируют друг друга через публичные точки входа. Это позволит подключить библиотеку к Optimizer или вынести её в отдельный репозиторий.

| Компонент          | Ответственность и публичная граница                                                                                                                                                                                                                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core`    | Принимает размеры, RGBA-пиксели и время кадра. Определяет тип экрана, выделяет показы предметов, выбирает область карточки. При распознавании вызывает переданную функцию OCR и возвращает прочитанные поля с причинами сомнений. Пригоден и для одного изображения. Зависимости среды передаются снаружи. |
| `packages/good`    | Адаптер схем Genshin Optimizer. Предоставляет типы сохраняемых полей, ключи справочников, проверку готового артефакта и сериализацию GOOD. Имя источника экспорта задаёт вызывающее приложение.                                                                                                            |
| `packages/browser` | Принимает локальный `File`, декодирует видео браузером, предоставляет пиксели ядру, запускает OCR в worker, ограничивает очередь и освобождает ресурсы. Выдаёт прогресс и результаты по мере готовности. Поддерживает отмену и извлечение кадра по таймкоду для просмотра.                                 |
| `apps/web`         | React-интерфейс выбора файла, ленты предметов, редактирования и скачивания. Обрабатывает ошибки формата, даёт отменить сканирование и явно исключить нерешённые карточки.                                                                                                                                  |

Направление зависимостей — сайт → браузерный адаптер → ядро → GOOD. Сайт также использует GOOD при экспорте. Публичные типы ядра оперируют обычными числами, типизированными массивами, ключами и результатами OCR. Ядро тестируется с TypeScript без DOM-библиотеки. Встраивающее приложение может передать пиксели и собственную функцию OCR напрямую. Готовый браузерный адаптер доступен потребителям, которым нужен весь путь от видеофайла.

## Источник типов и справочников

В upstream источником формата служит Zod. На первом этапе закрепить commit SHA Optimizer, взять соответствующие схемы и таблицы ключей с их минимальными зависимостями. Хранить источник, ревизию и лицензию рядом с адаптированным кодом. Доменные типы выводить из схем через `z.infer`, тип экспортируемого артефакта получать из типа элемента `artifacts`. Временный результат распознавания строить из этих же типов полей с возможностью пропуска. Таймкод, свидетельства OCR и причины ручной проверки относятся к результату сканирования.

Перед передачей объекта upstream-схеме проверять обязательные поля и игровые ограничения. Некоторые поля схемы подставляют значения по умолчанию. Ошибка чтения должна оставаться видимой до правки. При обновлении закреплённой ревизии повторять тесты типов, контрольных кадров и импорта в Optimizer.

## Раскладки, языки и изображения

- **Раскладка.** Профиль находит видимую область игры и опорные элементы интерфейса, затем возвращает области вкладки, сетки, выделения, панели сведений и рисунка предмета. Координаты относительны к найденным элементам. Для v1 реализовать профиль ПК и проверить его на двух пропорциях. Соотношение сторон само по себе не служит причиной отказа. Если опоры не найдены, вернуть явный результат. Телефонный интерфейс добавляется отдельным профилем с собственными примерами, включая отличающиеся признаки выбора. Запись с телефона и запуск сканера в мобильном браузере проверяются независимо.
- **Язык игры.** Профиль английского задаёт модель OCR, отображаемые названия и соответствующие ключи GOOD, числовые разделители и маркеры вроде `(unactivated)`. Детектор переходов не зависит от словаря. Локаль интерфейса сайта и язык текста в записи задаются независимо. В первом релизе достаточно одного профиля без переключателя.
- **Картинка предмета.** Вырезать иллюстрацию из заголовка выбранной карточки. Она доступна ещё до успешного OCR, соответствует реально показанному предмету и не требует внешнего API. После выбора оставить маленькую миниатюру и таймкод. При редактировании показать увеличенный фрагмент с данными предмета.

## Обработка записи

1. Браузерный адаптер проверяет декодирование, читает размеры и длительность. Дешёвый проход детектора использует уменьшенные области. Для OCR сохраняется детализация исходного кадра.
2. Детектор пропускает оружие, меню и переходы, определяет устойчивый выбор предмета по панели и сетке. Наведение курсора на другую ячейку не завершает текущий показ. Два последовательных выбора предметов с одинаковыми характеристиками сохраняют отдельные записи.
3. Из каждого показа выбрать устойчивый резкий кадр. При перегрузке замедлить или приостановить чтение файла и при необходимости перечитать пропущенный интервал по таймкоду. Ограничить число ожидающих изображений. При спорном результате попробовать другой кадр того же показа, затем выдать одну карточку для проверки.
4. Пользователь видит миниатюры, таймкоды и спорные поля, может исправить любую карточку, выбрать владельца или исключить запись. Экспорт включает подтверждённые артефакты. В итогах видны количества включённых, исключённых и неподдерживаемых предметов.

## Этапы и приёмка

1. **Основа и распознавание одиночных кадров.** Создать Bun-workspaces, точки входа и Vite-сборки. Воспроизвести результат Optimizer на трёх PNG. Проверить перо +0 с неактивным DEF +23, четырёхзвёздочные часы ровно с двумя сабстатами и цветок +20 с четырьмя сабстатами. Проверить лицензию распространяемой OCR-модели и разместить worker, WASM и модель вместе с сайтом.
2. **Выделение предметов из видео.** До запуска OCR получить ленту ровно из **33** показов контрольного ролика в исходном порядке. Отдельно проверить начальное оружие, наведение, одинаковые экземпляры и повторяемость результата. Использовать дополнительные короткие примеры для сценариев, отсутствующих в ролике.
3. **Сквозное сканирование.** Соединить выделение показов с OCR и проверить поля по ручной разметке. Каждый из 33 предметов либо совпадает с эталоном, либо содержит явную отметку для проверки. Считать пропуски, повторы, ошибочно принятые карточки и количество ручных исправлений.
4. **Редактор и экспорт.** Пройти сценарий исправления и скачивания. Импортировать итоговый GOOD в Optimizer, сверить количество, владельцев, характеристики и неактивные строки. Проверить отмену, повторный выбор файла и отсутствие передачи кадров по сети.
5. **Готовность к выпуску.** Сверить работу на записях 16:9 и 16:10 в поддерживаемых браузерах, включая Safari на macOS. Замерить скорость и расход памяти на контрольной машине, повторить на длинной записи. Публикация статического сайта — отдельный шаг после приёмки.

Вести историю небольшими коммитами по проверяемым изменениям. Исходная папка `test-assets/` целиком исключена из Git. В ней уже есть контрольное видео `count-33.mp4` и PNG. Для публичных регрессионных примеров создавать отдельные производные изображения с непрозрачной заглушкой поверх игрового UID и очищенными метаданными. Проверять итоговые пиксели и список подготовленных к коммиту файлов. Для автоматической проверки ядра также использовать синтетические данные. Полный ролик остаётся локальным.
